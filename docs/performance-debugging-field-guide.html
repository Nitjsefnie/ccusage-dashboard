Performance debugging: a field guide

Every pitfall below is one an agent actually hit while taking a dashboard from an 8-second cold load to sub-second, together with the measurement that exposed it. None are hypothetical. The recurring shape is not "failed to find the bottleneck" — it is measured confidently, and measured the wrong thing.

The one-line version An unverified measurement is more dangerous than no measurement, because it ends the search. Most of the time lost below was spent optimising against numbers that were real but did not mean what they appeared to.

The loop

Work in this order. Steps 1 and 5 are the ones agents skip, and they are the ones that catch the errors.

  1. Measure what the user waits for — end to end, from their side. Not a component you can reach easily.
  2. Attribute it — split the total until the parts sum to the whole. A gap means missing instrumentation.
  3. Form one hypothesis, then design the experiment that could falsify it.
  4. Fix, and predict the delta before you measure it. A surprise means the model was wrong, not the fix.
  5. Re-measure end to end. Component-level improvement is not the deliverable.

Pitfalls

01

Measuring the layer you can instrument, not the one that hurts

Server-side timings for every endpoint looked healthy. The page still felt slow.

What was true
Four panel requests never started until the main query finished — a parallel fan-out had silently become a serial chain. Each endpoint, measured alone, was fine.
Found by
A browser HAR waterfall. Nothing server-side can see this: no single request is slow, only their arrangement.
Cost
The agent introduced this regression while optimising, then reported success twice before a HAR arrived.
RuleBefore claiming a page is faster, get a client-side waterfall. Server timings cannot express request ordering, and ordering is often the whole problem.
02

A readiness signal that does not mean ready

The protocol was: restart the service, wait for the ingest to report finished, then measure. It looked rigorous.

What was true
finished_at was written to the run table before the derived-state rebuilds ran. Every "clean" measurement was taken while heavy write passes were still executing.
Found by
Reading the order of statements in the ingest function — after wondering why identical code measured 6.0s and 1.4s minutes apart.
Cost
A whole session of cold numbers inflated ~4×, and a confident but wrong attribution to buffer-cache effects.
RuleVerify what your readiness signal actually gates. If you wait on a flag, read the code that sets it. Prefer waiting on the observable you care about — a log line from the last step, not a status field written by an earlier one.
03

Naming a cause you never measured

Five concurrent requests each took ~3.2s while their own bodies took under 900ms. The agent attributed the gap to interpreter-level contention. It sounded right.

What was true
The rebuild used TRUNCATE, which holds an ACCESS EXCLUSIVE lock for the whole transaction. Every concurrent reader blocked on it.
Found by
A 30-second experiment: open a transaction that truncates and sleeps, time a SELECT from another connection.
SELECT during TRUNCATE txn : 2.88s
SELECT with nothing in flight : 0.07s
RuleA plausible mechanism is a hypothesis, not a finding. Before naming a cause, ask what experiment separates it from the alternatives — then run it. Contention explanations are especially seductive because they are unfalsifiable until you try.
04

Instrumentation with holes reads as completeness

Per-phase timings were added and trusted. Two blind spots survived the entire session.

Hole one
The timer wrapped cursor.execute() but not fetchall(), so materialising rows was invisible — about 554ms of a 2.5s request.
Hole two
The log handler was attached to the api child logger; ingest logged under a sibling. Four rebuild log lines were silently discarded for hours.
The tell
The named phases summed to less than the reported total. That arithmetic gap is the signal — it was visible in the logs long before anyone read it.
RuleMake the instrument account for the whole. Emit both the sum of parts and the measured total, and treat any divergence as an unmeasured phase. Then verify the output actually appears — instrumentation that logs nowhere is indistinguishable from a fast system.
05

Optimising a real bottleneck that is not the user's bottleneck

Deduplication was moved from read time to ingest time — a genuine, well-verified improvement.

Result
Transformative for one endpoint that repeated the work four times per request (19.1s → 0.52s). A wash for the main dashboard, which had been amortising it across six queries: the work simply redistributed.
Lesson
"This step is expensive" does not imply "removing it makes the request faster." It depends on what else shares the cost.
RulePredict the end-to-end delta before doing the work. If you cannot predict it, you do not understand the cost structure well enough to be optimising yet — and report the wash honestly when it happens.
06

Improving something nothing consumes

A field was found to be reporting 67,969 where the true value was 2,173, and the query was carefully corrected.

What was true
No frontend file read that field. It was deleted shortly afterwards, along with three others and about 2 MB of response body.
Found by
A test that walks every API response and asserts each field name appears somewhere in the client source.
RuleConfirm a consumer exists before optimising, or fixing, a producer. The cheapest performance win is deleting work nobody asked for — check that first, not last.
07

Hand-derived cache keys drift from real ones

A pre-warmer populated the cache at startup. A later change added a parameter to one endpoint.

What was true
The warmer fell back to the endpoint's signature default (30d) while the UI opens on all. The single request every page load makes was warmed under a key nothing would ever request.
Why it hid
Nothing failed. The cache worked; it was merely full of the wrong entries. Only a timing measurement of a supposedly-warm path exposed it.
RuleDerive keys from the same code path the real request uses, never by restating the parameters. Then assert coverage in a test that enumerates what the client can actually ask for.
08

Porting a query by reading it

An expensive query was precomputed into a table. The port was reviewed carefully and looked correct.

What was true
The original selected GREATEST(1, CEIL(n * 0.01)); the port wrote GREATEST(n / 100, 1). Integer division floors, so at n=150 one produced 2 rows and the other 1.
Found by
Diffing the precomputed table against the live query over the full dataset — not by re-reading the SQL.
RuleVerify a derived store by differencing it against the source of truth over real data, comparing every column. Review catches typos; only a diff catches semantics.

Techniques that paid

Env-gated instrumentation that ships

Per-phase timing read from an environment flag once at import, inert when off, committed with the fix rather than removed after the measurement. Reconstructing a query path by hand in a REPL drifts from what the service actually runs and omits everything outside the part you rebuilt — which is exactly how pitfall 04 hid.

CaveatIts weakness is the mirror of its strength: a flag left off makes the tooling invisible. One port of this work sat with instrumentation present but unset, and produced silence that looked like a hung service.

Precompute at ingest, and know what cannot be

Sums, counts and extrema compose across buckets, so they can be stored fine-grained and rolled up. Percentiles do not. The escape hatch is that display buckets are usually epoch-aligned and few: compute the percentile once per bucket width and let a range filter select buckets. Exact, not approximated — no accuracy traded away.

Rebuild in place without locking readers

DELETE plus re-insert inside one transaction takes a row-level lock, and MVCC keeps serving the previous rows until commit. TRUNCATE is faster in isolation and blocks every reader for the duration. At a few thousand rows the difference in raw speed is noise and the difference in user-visible stalling is total.

Pre-flight checklist

  • Do I have an end-to-end measurement from the consumer's side, not just component timings?
  • Does my readiness signal actually mean the system is idle? Have I read the code that sets it?
  • Do my instrumented phases sum to the measured total? Where is the gap?
  • Is my instrumentation's output actually appearing, or am I reading silence as success?
  • Have I stated the cause as a hypothesis and named the experiment that would falsify it?
  • Did I predict the end-to-end delta before measuring it?
  • Does anything actually consume what I am about to optimise?
  • If I derived a store or a key, have I diffed it against the source of truth over real data?
  • Have I re-measured end to end, including the regression I may have just introduced?
