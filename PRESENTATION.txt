# :computer: claudit
### where your Claude Code tokens actually go

I kept eyeballing my Claude Code spend, so I built something that stops guessing. It ingests session JSONL transcripts into Postgres and serves 10 panels: burn rate, cost by model, token breakdown, prompt-cache TTL split, per-session context growth, response sizes, tool usage, reply latency, tool error rate, and a weekday×hour activity heatmap.

## :globe_with_meridians: Try it right now — nothing to install
**https://claude.nitjsefni.eu/** → click *Continue as guest*

Read-only, no signup, loaded with my real data. Poke at every panel before you decide whether it's worth pointing at your own transcripts.

Against my own history: **9,284 transcripts** · **1,400 sessions** · **302.3k requests** · **68 projects** · **62.4B tokens** · **$53.5k** · Jan–Jul 2026 — that's what you'll be clicking through.

## :bug: Why another usage tool
Most of them quietly get the accounting wrong. Two that bit me:

:warning: Claude Code writes one JSONL line per content block of a streamed reply — all sharing `message.id` + `requestId` — and only the last line carries the true `output_tokens`. Keep the first and you silently lose **~32% of all output tokens**.

:warning: Cache *writes* are priced by TTL: 5m at 1.25× input, 1h at 2×. Flatten that to one rate and every 1h write is undercharged by **37.5%**. **73.1%** of my cache writes were 1h.

:gear: claudit does per-requestId max-merge, TTL-split pricing, dated rate changes (Sonnet 5's intro price runs out Aug 31), and cross-file uuid dedup so sub-agent transcripts don't double-count their parent — 3.5% of my records are cross-file duplicates.

:mag: It also refuses to invent a price. An unrecognised model falls back to its family's rates and the response flags the figure as estimated, rather than presenting a guess as fact.

## :test_tube: Correctness
**156 tests.** One walks every API response and asserts each field is actually read by the frontend — it found four that weren't, including 1 MB of context traces duplicating another field, and a `file_count` reporting 67,969 files for a project that has 2,173.

## :tools: Stack
FastAPI + Postgres + React with **no build step** — in-browser Babel, no npm, no bundler. Ingest pulls from Cloudflare R2 or a local directory; there is no upload path, by design.

## :lady_beetle: Follow-up: I was storing one tool call in four

The last post was about bugs *other* tools have. Here's one of mine, found after I'd already shipped the thing.

Claude Code writes one JSONL line per content block. A turn's tool calls therefore land on lines **after** the first line of their `requestId` — so extracting them only from that first line silently drops the rest. Measured across three of my own sessions, the share of `tool_use` blocks sitting on a later line:

```
520 blocks -> 370 dropped   71%
545 blocks -> 313 dropped   57%
401 blocks -> 271 dropped   68%
```

The comment defending it said streaming duplicates carried the same blocks, so only the first should count. That premise was simply false: block count equalled *distinct id* count in every transcript I checked (520/520, 545/545, 401/401). There were no duplicates. It was discarding real calls to solve a problem that did not exist.

Reparsing everything after keying on the globally-unique block id instead:

```
tool calls recorded   80,750  ->  309,043
Bash                  38,950  ->  154,307
Read                  20,150  ->   67,119
```

**Roughly one call in four was making it into the database.** Every tool-usage and tool-error-rate number I have published until now was drawn from that quarter.

Three things worth taking from it:

:one: **The dangerous comment is the one that sounds reasonable.** "Streaming dupes shouldn't be double-counted" is a real concern, so nobody questioned whether it applied here. Checking took one line: compare block count to distinct-id count.

:two: **Two other implementations were already right.** The canonical parser and the in-browser one both parse content outside the requestId branch, gating only the token merge. My backend was the odd one out — a port that drifted, not a design decision. Three implementations of one spec means two can quietly disagree with the third.

:three: **The totals looked fine throughout.** Cost, tokens and request counts were all correct, because the bug touched only tool extraction. Nothing about the dashboard looked broken — the tool panels just showed a smaller world than the real one.

:mag: Credit to @Floral-Overcast, who found it in a fork and fixed it there. I verified it independently before porting — a good reminder that "the numbers look plausible" is not a test.
